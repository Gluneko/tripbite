# 「食途 TripBite」— 旅行美食规划 Agent 实战项目蓝图

> 4 周全职冲刺 · Claude Agent SDK + MCP · 带评测与可观测的开源作品集项目
> 目标：面试时能回答"你怎么知道你的 Agent 变好了"，而不只是"我搭过一个 Agent"

## 1. 一句话定位

**输入**：目的地、日期、预算、口味偏好、同行人数
**输出**：一份可执行的行程方案 —— 机票/酒店候选、逐日路线（含通勤时间）、每餐餐厅推荐（带推荐理由和口味匹配依据）
**背后**：多 Agent 编排 + MCP 工具链 + 约束校验器 + 回归评测集 + 全链路 tracing

差异化不在"又一个旅行 Agent"，而在两点：

1. **口味画像层**：把大众点评橙 V6 多年的收藏/评价数据做成用户口味画像（Memory），推荐餐厅时 Agent 引用画像做个性化排序——独有的真实数据和产品洞察。
2. **评测先行**：行程规划是少数能自动判分的 Agent 场景（预算超没超、餐厅营业时间冲不冲突、两点间通勤时间可不可行，全是确定性检查）。

## 2. 三个 Demo 场景（也是评测集的种子）

1. **常规**："十一去成都 4 天，两人预算 6000，爱吃辣但同伴不能吃太辣，要一顿火锅一顿苍蝇馆子，住春熙路附近。"
2. **强约束**："周五晚到大阪、周日下午走，预算紧，不吃生食，酒店必须近地铁，帮我塞进两家米其林必比登。"
3. **对抗性**："预算 800 去三亚玩五天住海景房" —— 正确行为是指出预算不可行并给出替代方案，而不是硬编一个假行程。

## 3. 系统架构（目标态）

```
用户输入
   │
   ▼
┌─────────────── Orchestrator (Claude Agent SDK 主循环) ───────────────┐
│  意图解析 → 任务分解 → 调度子Agent → 汇总 → 交给 Verifier → 输出      │
└──────┬──────────────┬──────────────┬──────────────┬────────────────┘
       ▼              ▼              ▼              ▼
  Transport      Stay Agent     Food Agent     Route Agent
  Agent          (酒店检索+     (餐厅检索+     (高德MCP:
  (航班/火车     筛选)          口味画像       路线/通勤/
   MCP)                        匹配排序)      POI/天气)
       │              │              │              │
       └──────────────┴──────┬───────┴──────────────┘
                             ▼
                    Itinerary Planner（逐日排程）
                             ▼
              ┌── Verifier 层（幻觉与约束治理）──┐
              │ ① 确定性校验器（纯代码，非LLM）  │
              │ ② Critic Agent（LLM 复核）      │
              └────────┬───────────────────────┘
                       ▼
            不通过 → 带失败原因打回 Planner 重排（最多 N 轮）
            通过   → 输出行程 + 引用来源
                             ▼
                  Memory 层（口味画像、历史行程偏好）
```

**架构决策要点：**

- 为什么多 Agent 而不是单 Agent 多工具：检索类任务上下文膨胀快，子 Agent 隔离上下文、只回传结构化结果。要有消融对比。
- 为什么 Verifier 用"代码校验 + LLM 复核"双层：能用代码判的绝不用 LLM 判；LLM 只判代码判不了的。
- 重试策略：Verifier 打回时带结构化失败原因，Planner 定向修复而不是整体重生成。

## 4. 工具层（MCP）清单

- 高德地图官方 MCP Server：POI 搜索、路线规划、通勤时间、天气
- 航班/火车：12306 社区 MCP 或航班搜索类 MCP；找不到合适的就 mock
- Web Search：餐厅口碑、景点近况的兜底检索
- **自写 `taste-profile-mcp`（W2）**：解析大众点评收藏/评价数据 → `get_taste_profile`、`match_restaurant` 两个 tool，发布到 npm/GitHub

## 5. 上下文工程与成本控制

- 子 Agent 回传结构化 JSON，不回传原始网页/长文本
- 模型分级：检索/抽取用便宜模型，规划与 Critic 用高档模型
- Prompt 缓存 + compaction
- 每次运行输出成本小票

## 6. 评测体系（W3 重点）

**第一层：确定性检查**（预算/时间/地理/硬约束/格式，纯代码判分）
**第二层：LLM-as-judge**（个性化契合度、取舍解释质量；judge 与 20 条人工标注对齐并报告一致率）
**第三层：回归评测集 + CI**（40-50 case：10 常规 / 15 强约束 / 10 对抗性 / 5-10 真实需求；GitHub Actions 每 PR 跑分）

## 7. 可观测性

- Langfuse 全链路 trace（每子 Agent、每 tool call、token 与延迟）
- 失败分类：工具报错 / 幻觉被拦 / 约束不满足 / 超时
- 2-3 个真实 debug 案例写进 README（带 trace 截图）

## 8. 四周里程碑

- **W1 最小闭环**：脚手架 + 高德 MCP + 单 Agent 跑通成都场景；结构化 JSON + Markdown；ADR v1。交付：CLI demo
- **W2 多 Agent + 自写 MCP**：4 子 Agent 编排 + 消融对比；taste-profile-mcp；确定性 Verifier v1。交付：多 Agent 版本 + MCP Server 发布
- **W3 评测 + 可观测**：40+ case 判分脚本；Langfuse；LLM-as-judge + 人工标注；CI；一轮真实优化留 before/after。交付：CI 评测报告 + trace 面板 + 成本对比
- **W4 打磨放大**：README 大修、demo 视频（中英）、简历更新、内容发布。交付：完整 repo + 视频 + 新简历

**降级预案**：砍单项顺序 Web 界面 → 双语视频 → 航班真实数据（用 mock）。评测和 tracing 永远不砍。

## 9. 风险与应对

- 大众点评无 API：不爬，手动导出收藏几十条即可——卖点是"个人真实数据建模成 Agent memory"这个设计
- 旅行 Agent 太常见：靠口味画像 memory、对抗性 case 诚实拒绝、完整评测体系拉开差距
- 4 周做不完：W1 最小闭环优先；每周五强制 GitHub release
