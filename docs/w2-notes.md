# W2 里程碑：确定性 Verifier + 打回重排闭环

场景同 W1：成都 4 天 / 两人 6000 / 辣度矛盾 / 火锅+苍蝇馆子 / 春熙路。

## 打回重排实测（2026-08-13）

| 轮次 | 校验错误 | 成本 | 说明 |
|---|---|---|---|
| R0 首次生成 | 7 | $0.49 | 4×账目不闭合 + 总额不一致 + 苍蝇馆子绕路 5.76km ×2 |
| R1 定向修复 | 1 | $0.16 | 模型自己补了地铁 transit 项、重分摊了逐晚房费；仅剩通勤预留 30<35 分钟 |
| R2 定向修复 | 0 | $0.14 | 通过全部校验 |

**关键数字**：定向重排一轮 ≈ 全量重生成成本的 1/3（session resume 保留工具上下文 + prompt 缓存命中，input 从 5 万降到 4-5 千）。重排指令由 `toRepairInstructions()` 从结构化 `VerifyIssue` 生成——修哪条、差多少、怎么修，全部定向。

## 本轮新发现 → 已修

- **"哭穷后门"**：R2 修完数字后总花费 5926 已在预算内，但 `budgetFeasible` 仍为 false、budgetNotes 还引用旧的 6422。而 feasible=false 会跳过超预算检查——等于模型可以靠"声称不可行"绕过预算校验。已加规则 `budget.feasibility-mismatch` 堵上（17 个单测）。

## 已知缺口（记入 W3 评测层的活）

1. **年份幻觉**：模型把"十一"解析成 2025-10-01（应为 2026）。日期合法性校验需要注入"今天"作为参照，属评测 harness 的 case 规格（避免校验器引入非确定性）。
2. **budgetTotal 漂移**：用户说 6000，最终输出 budgetTotal=5926（模型把"总花费"填进了"预算"字段）。校验器只看行程 JSON 内部一致性，"输出与用户原始需求的一致性"要靠评测集的 case 期望值来判。
3. 渲染小瑕疵：大交通 transit 项缺 transitMode 时 Markdown 显示空括号。

## 跨模型对比：同一场景 GLM-4.7 vs DeepSeek（2026-08-14）

后端切换只改了 .env 三行（Anthropic 兼容端点的价值）。同一成都场景：

| 指标 | GLM-4.7（3 次运行） | DeepSeek deepseek-chat |
|---|---|---|
| 首轮校验错误 | 7 / 8 / 6 | **0（零打回直接通过）** |
| 工具调用次数 | 19-29 | 66（两批酒店询价、逐段真实路线） |
| 年份解析 | 一直写成 2025 | 正确（2026-10-01） |
| 返程早班车处理 | 自编 12:30 班次 | 尊重 08:02，Day4 不排游览 |
| output tokens | 6-12k | 49k（含自发任务清单管理） |
| 实际成本/次 | ~¥1-2（智谱按量估） | **~¥0.3-0.5**（缓存命中 ¥0.02/M） |

**taste-profile 实测**（DeepSeek 运行）：首个工具调用即 get_taste_profile；两轮 match_restaurants；
成都吃客 52 分因排队雷点被淘汰、千牛刀渣渣牛肉因牛肉信号入选、明婷 60 分但"用户明确要求
优先于画像"被保留——排序器不否决规则被正确执行；推荐理由全部引用画像证据（"4 家牛肉主题店
≥4.5 星"）。个性化推荐从"套话"到"带证据"的跃迁完成。

注意：单次运行样本，不能下"DeepSeek 更强"的结论——这正是 W3 要用 40+ case 评测集回答的问题。
但它已经证明了评测基建的价值：换模型后 5 分钟就能拿到可对比的质量信号。

## 单 Agent vs 多 Agent 消融对比（2026-08-14，DeepSeek，同一成都场景）

| 指标 | 单 Agent | 多 Agent（Orchestrator + 4 子 Agent） |
|---|---|---|
| 首轮校验错误 | **0** | 4（酒店项零时长 ×3、候车项贴发车时刻） |
| 总耗时 | **393s** | 664s（+69%） |
| 成本（牌价折算） | **$1.98** | $2.91（+47%，含 $0.41 修复轮） |
| input / cacheRead | 96.8k / **611.7k** | 122.8k / 296.4k（缓存命中率显著更低） |
| output | 47.6k | 86.0k |
| 检索发现 | 骆孃孃 91 分、探索位自力面店 | 唐家寺鲜牛杂火锅（熊猫基地旁，牛肉+火锅双命中）、谭豆花探索位、为控预算主动砍武侯祠门票 |
| 涌现行为 | — | Orchestrator 用 SendMessage 追问 transport 子 Agent"有没有更晚的返程班次" |
| 溯源完整性 | 全部 POI 坐标工具透传 | **景点坐标为"常识估算"**（编排 prompt 允许景点免检索的副作用，warnings 里诚实声明了） |

**结论（单场景样本，n=1）：**

1. 在当前任务规模（4 天行程、~100k input）下，**单 Agent + 确定性校验器是更优默认**：
   更快、更便宜、首轮零错误。蓝图假设"检索类任务上下文膨胀快、需要子 Agent 隔离"在这个
   规模下未被验证——上下文还不是瓶颈。
2. 多 Agent 的错误模式很有代表性：**信息经过 JSON 摘要压缩后，编排者拼装时引入了
   单 Agent 不会犯的排程错误**（酒店项零时长、候车贴点）。隔离上下文的代价是信息保真度。
3. 多 Agent 的真实收益也可见：工具面收窄后子 Agent 检索更聚焦（挖到了熊猫基地旁的
   牛杂火锅）；缓存命中率低是结构性代价（各子 Agent 上下文独立，吃不到主会话缓存）。
4. 待修：多 Agent 模式的景点坐标未走工具透传（geo 校验形同虚设）——应把景点坐标
   纳入 route 子 Agent 的职责。
5. 下一步用 W3 评测集在更大任务（7 天多城）上复测——预期上下文压力增大后天平会向
   多 Agent 倾斜，届时才有资格下最终结论。

## 面试叙事素材

- "怎么知道 Agent 变好了"：R0→R2 的错误数与成本曲线，就是最小可展示的答案。
- "重试策略为什么不整体重生成"：R1 的 input token 只有 R0 的 1/10，且不会丢失已确认的 POI。
- "校验器为什么不用 LLM"：`budget.feasibility-mismatch` 这种规则一行代码判死，LLM judge 反而可能被 budgetNotes 的合理化说辞带偏。
